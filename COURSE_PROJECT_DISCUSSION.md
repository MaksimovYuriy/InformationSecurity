# Курсовой проект: проверка безопасности облачного хранилища

## Назначение документа

Этот документ предназначен для обсуждения проекта с одногруппником. Он фиксирует понимание задания, возможный объём работы и вопросы, которые нужно решить перед составлением подробного плана разработки.

Стек, провайдер и набор правил ниже — предложения, а не принятые решения.

## 1. Исходное задание

**Тема 15. Проверка безопасности облачного файлового хранилища.**

- Проблема: ошибки настройки могут открывать посторонним доступ к файлам.
- Основное задание: разработать службу проверки безопасности облачных хранилищ, подготовить 6–10 правил, обнаруживать общедоступные хранилища и формировать рекомендации.
- Самостоятельная часть: обосновать состав проверок и оценить опасность обнаруженных нарушений.
- Испытания: обнаружить открытый доступ к учебному хранилищу и подтвердить исправление.
- Дополнительное задание: ИИ-помощник, объясняющий ошибки доступа и составляющий план исправления настроек конкретного хранилища.

## 2. Как мы понимаем проект

Нужно разработать приложение для аудита существующего облачного хранилища. Создавать собственное хранилище не требуется.

Предполагаемый сценарий:

1. Пользователь указывает облачный аккаунт, проект или хранилище.
2. Приложение получает конфигурацию через API провайдера.
3. Движок правил проверяет настройки доступа и защиты.
4. Пользователь получает отчёт: обнаруженные нарушения, доказательства, уровни опасности и рекомендации.
5. После изменения настроек повторная проверка показывает, устранены ли нарушения.

**Первое решение:** выбрать тип сервиса. Объектное хранилище с бакетами и объектами и облачная файловая система — разные типы сервисов; выбранный вариант нужно явно зафиксировать в границах проекта.

Возможное уточнённое название: «Разработка службы проверки безопасности объектного хранилища [провайдер] с оценкой рисков и формированием рекомендаций».

## 3. Предлагаемый объём

### Обязательная версия

- Один облачный провайдер и один тип хранилища.
- Получение конфигурации с минимальными необходимыми правами чтения.
- 6–10 обоснованных правил; предварительный ориентир — восемь.
- Обнаружение публичного доступа.
- Оценка опасности и рекомендации по каждому нарушению.
- Сохранение отчёта и сравнение результатов до и после исправлений.
- Воспроизводимый учебный стенд и протокол испытаний.
- Инструкция запуска и пояснительная записка.

### Возможное расширение

- ИИ-помощник для объяснения результатов и подготовки плана исправления.
- Веб-интерфейс, если для основной версии достаточно API или командной строки.
- Периодический запуск проверок и история аудитов.
- Развёртывание стенда средствами инфраструктуры как кода.

### Предлагаем оставить за рамками первой версии

- Поддержку нескольких провайдеров.
- Анализ содержимого файлов и поиск персональных данных.
- Автоматическое исправление конфигурации.
- Корпоративную систему пользователей и ролей самого аудитора.

## 4. Кандидаты в правила проверки

Окончательный набор определяется после выбора провайдера и изучения его модели доступа. Нельзя заранее считать, что все перечисленные механизмы доступны через его API.

| № | Проверка | Возможные последствия |
|---|---|---|
| 1 | Анонимное чтение объектов | Утечка содержимого файлов |
| 2 | Анонимное получение списка объектов | Раскрытие имён файлов и структуры хранилища |
| 3 | Анонимная запись или загрузка | Размещение посторонних файлов, подмена данных, расход ресурсов |
| 4 | Анонимное удаление объектов | Потеря данных и нарушение доступности |
| 5 | Доступ внешних аккаунтов вне разрешённого списка | Доступ нежелательных третьих лиц |
| 6 | Избыточные права пользователей или сервисных аккаунтов | Увеличение ущерба при компрометации учётной записи |
| 7 | Отсутствие механизма предотвращения случайного публичного доступа | Возможность случайного открытия хранилища |
| 8 | Возможность обращения без защищённого соединения | Раскрытие данных при передаче |
| 9 | Отсутствие журналирования значимых операций | Сложность обнаружения и расследования инцидентов |
| 10 | Отсутствие восстановления после удаления или перезаписи | Увеличение последствий ошибочных и вредоносных действий |

Для правил 5 и 6 потребуется определить допустимые аккаунты и необходимые права: без этой информации нельзя достоверно определить нарушение.

Правила 1–4 проверяют разные операции. Доступ к списку объектов не обязательно даёт доступ к содержимому; возможность загрузить объект не обязательно позволяет удалить существующий.

Нужно учитывать итоговое действие всех политик, ACL и запретов, а не только наличие отдельного разрешения. Намеренно публичные ресурсы должны поддерживаться как согласованные исключения.

Предлагаемые статусы результата:

- нарушение подтверждено;
- обнаружен потенциальный риск;
- нарушение не обнаружено;
- недостаточно данных или прав для проверки;
- правило неприменимо.

## 5. Самостоятельная аналитическая часть

Для каждого выбранного правила подготовить карточку:

1. Угроза и причина включения проверки.
2. Анализируемые настройки и источник данных.
3. Условия обнаружения нарушения.
4. Исключения, ограничения и возможные ложные срабатывания.
5. Критерии оценки опасности.
6. Рекомендация по исправлению.
7. Способ подтверждения исправления.

Предлагается оценивать риск по вероятности и последствиям. Учитывать доступность из интернета, разрешённые операции, чувствительность данных, охват объектов и возможность восстановления. Методика должна быть прозрачной и одинаковой для всех проверок.

Если содержимое файлов не анализируется, чувствительность данных можно задавать вручную или через метки ресурса. Отсутствие этой информации следует явно отражать в отчёте.

## 6. Предварительная архитектура

```text
Интерфейс пользователя
         |
     API службы
         |
Сбор конфигурации через SDK провайдера
         |
    Движок правил
         |
Оценка риска и рекомендации
         |
Хранилище результатов и отчёт
         |
ИИ-помощник (дополнительно)
```

Предполагаемые компоненты:

- Адаптер провайдера для получения конфигурации.
- Независимые проверки с единым форматом результата.
- Модуль оценки риска и шаблоны рекомендаций.
- Хранилище запусков аудита и обнаружений.
- Экспорт отчёта в машиночитаемом и удобном для человека формате.
- API, командная строка или простой веб-интерфейс — по согласованию.

Возможный стек для обсуждения: Python, FastAPI, официальный SDK провайдера, SQLite, Docker. Выбор зависит от возможностей API провайдера, формата интерфейса и способа развёртывания.

В результате проверки хранить: ресурс, правило, время, статус, уровень риска, описание, доказательства, рекомендацию и способ проверки исправления. Учётные данные не должны попадать в отчёты и журналы.

## 7. Дополнительная часть: ИИ-помощник

Помощник получает структурированные результаты аудита и формирует объяснение проблемы, последствия и последовательность исправлений для конкретного ресурса.

Предлагаемые границы:

- Нарушения определяет движок правил; ИИ объясняет уже полученные результаты.
- В запрос передаются только необходимые данные без секретов и содержимого файлов.
- Ответ должен учитывать выбранного провайдера и обнаруженные настройки.
- План исправления проверяется на учебном стенде.

Нужно выбрать формат: помощник, формирующий объяснения, или агент с инструментами. Для агента отдельно определить его действия: например, получение результатов аудита и запуск повторной проверки. Автоматическое изменение настроек — самостоятельное расширение объёма.

## 8. Учебный стенд и испытания

Использовать отдельный учебный проект и искусственные файлы. Изменения доступа выполнять только на ресурсах стенда.

Основной сценарий защиты:

1. Создать закрытое хранилище с тестовым файлом.
2. Подтвердить отсутствие анонимного доступа.
3. Включить публичное чтение.
4. Запустить аудит и получить нарушение с доказательствами.
5. Независимым запросом без облачных учётных данных подтвердить доступ к файлу.
6. Исправить настройку по рекомендации.
7. Повторить анонимный запрос и подтвердить отказ.
8. Повторить аудит и показать устранение нарушения.
9. Сохранить отчёты до и после исправления.

Дополнительные сценарии: известная ошибочная конфигурация для каждого правила, безопасная конфигурация, согласованное исключение, недостаточные права аудитора. Проверки записи и удаления проводить на специально созданных тестовых объектах.

Оценивать число обнаруженных подготовленных нарушений, пропусков и ложных срабатываний, корректность повторной проверки и длительность аудита.
