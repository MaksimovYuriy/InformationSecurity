# Итерация 4: сбор и нормализация конфигурации

## Результат

Итерация завершена: получен структурированный снимок учебного бакета VK Cloud, сохранён локально и прочитан отдельным CLI-процессом. Доступные ACL и версионирование сопоставлены с отдельными запросами SDK к облаку. Ограничения API и охвата отражены явно; заключения о безопасности не формируются.

## Архитектура и контракт

- `domain/snapshot.py`: `ConfigurationObservation` и `ConfigurationSnapshot`, независимые от SDK и CLI.
- `application/snapshot.py`: интерфейсы `ConfigurationCollector`, `SnapshotRepository` и сервис `SnapshotService`.
- `infrastructure/s3_configuration.py`: восемь запросов чтения и нормализация ответа S3. `S3Provider.collect` делегирует этому сборщику.
- `infrastructure/snapshots.py`, `snapshot_schema.py`: атомарное JSON-хранилище и проверка версии/структуры снимка.
- CLI: `collect --resource NAME [--profile vk] [--format json|text]` и `snapshot ID [--format json|text]`. Для `collect` профиль по умолчанию и единственный допустимый — `vk`; чтение `snapshot` не требует ключей и не обращается к облаку.

`collect` обращается непосредственно к указанному бакету, без предварительного перечисления всех бакетов. Имя бакета не сохраняется в глобальной конфигурации подключения.

Снимок версии 1 содержит UUID, провайдера, идентичность ресурса, время начала сбора в UTC, охват, ограничения, общий статус и восемь наблюдений. Наблюдение содержит имя настройки, исходный метод, статус, нормализованные данные либо безопасную причину отсутствия данных. Неизвестные условия и конструкции политики сохраняются в JSON-документе без интерпретации. SDK ResponseMetadata, заголовки запросов, ключи доступа и содержимое файлов в снимок не включаются. Идентификаторы владельцев/грантополучателей, ARN, политики и имена целевых бакетов могут присутствовать как необходимые данные конфигурации; снимки следует хранить локально.

Статусы наблюдений:

- `available`: настройка прочитана и нормализована;
- `absent`: API явно сообщает об отсутствии конкретной настройки; для журналирования это также отсутствие `LoggingEnabled` в успешном ответе;
- `access_denied`: недостаточные права, данные неизвестны;
- `unsupported`: API вернул NotImplemented/UnsupportedOperation, состояние защиты неизвестно;
- `error`: сеть/SDK, лимит, другая ошибка сервиса или повреждённый ответ, данные неизвестны.

Отсутствующий `Status` в успешном `GetBucketVersioning` означает `Disabled` согласно контракту S3. Отсутствующий `MFADelete` сохраняется как `null` (неизвестно), а не как отключённая защита. Отсутствие политики не означает отсутствие публичного доступа через ACL.

`complete_for_scope` означает, что все восемь настроек прочитаны либо явно отсутствуют. Если есть `access_denied`, `unsupported` или `error`, статус — `partial`. Код завершения `collect` и `snapshot`: 0 для полного сбора в выбранном охвате, 3 для частичного снимка. При ошибке идентификации ресурса, отозванных/некорректных ключах, повреждённом или просроченном локальном снимке — 2; ошибка файлового доступа — 1. `NoSuchBucket` и ошибки авторизации прерывают сбор без сохранения частичного артефакта.

## Охват и хранение

- Только настройки бакета. Объекты не перечисляются, их ACL и содержимое не запрашиваются. Неприменимость объектных проверок в этом режиме отражается охватом и ограничениями, а не вымышленными результатами о файлах.
- Настройки уровня аккаунта не собираются. Результаты запросов идут последовательно и не образуют атомарного снимка облака.
- API Block Public Access и шифрования по умолчанию, если доступны, описывают только настройки бакета, а не все механизмы защиты провайдера и объектов.
- Каталог `STATE_DIR/data/snapshots` имеет права 0700, файлы — 0600. Запись через временный файл, fsync и атомарную замену; сбой замены сохраняет прежний файл.
- Предел одного JSON — 2 МиБ. Идентификатор, версия схемы, источник/статус/форма данных, полнота набора полей и согласованность статуса проверяются при чтении и сохранении. Символические ссылки на файлы снимков отклоняются.
- Срок хранения — 7 суток от начала сбора. Просроченные снимки не выдаются; удаление корректных просроченных файлов выполняется при следующем сохранении. Фонового планировщика удаления нет; пока приложение не запускается, файлы могут физически оставаться на диске. Повреждённые и посторонние файлы автоматически не удаляются.

## Проверки

TDD: сначала тесты упали на отсутствии `application.snapshot`; после реализации прошли проверки нормализации, частичных данных, отсутствующего ресурса, авторизации, области охвата и хранения. Тест CLI отдельно сначала упал на неизвестной команде `collect`. Дополнительные тесты выявили ошибочную трактовку отсутствующего MFADelete и недостаточную проверку вложенных сохранённых данных; обе исправлены после воспроизведения.

Полный прогон: **28 тестов успешно** (15 прежних, 13 новых). Проверены также Stubber настоящего SDK, чтение снимка другим процессом без ключей, версия схемы, попытка обхода пути, испорченные поля, права файлов, семидневное хранение и сбой атомарной записи.

Итоговый проверенный снимок: `c18d51692d0940559c7ed611bc55144a` в локальном `.state/data/snapshots`; имя бакета и конфигурация в этот протокол не копируются. Проверка не изменяла настройки облака и не скачивала файлы. Положительные ответы политик, шифрования, журналирования, Object Lock и Block Public Access проверены локальными сценариями; реального наличия этих настроек на стенде не утверждаем.

Итерация 5: интерфейс правил, статусы проверок, доказательства, модель риска и первое правило.
