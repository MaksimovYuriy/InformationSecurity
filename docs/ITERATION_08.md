# Итерация 8: история, отчёты и повторная проверка

## Статус

Завершена. Новые запуски сохраняются в SQLite, доступны фильтры, JSON/Markdown, явный импорт прежних JSON и объяснимое сравнение. Реальный изолированный сценарий VK Cloud подтвердил новые и устранённые нарушения по read/list; временный стенд удалён. Ошибка запроса отдельно записана в историю и не выдана за устранение.

## Архитектура и хранение

- `domain/history.py`: модели запроса/страницы истории, контекста сравнения и переходов обнаружений.
- `application/history.py`: сервис и интерфейс истории. `application/comparison.py`: независимые от SQLite/CLI правила сравнения.
- `infrastructure/history.py`: SqliteReportRepository; `formatting.py`: представления, Markdown и приватный экспорт.
- Новый основной путь: `STATE_DIR/data/audit.sqlite3`, схема БД user_version=1. `runs` хранит идентичность, времена, статус, параметры и канонический JSON отчёта; `run_rules` — индексируемые результаты/выбранные правила. Родительские записи и результаты сохраняются одной транзакцией.
- Завершённые и неполные отчёты включают полный контекст политики, охват, снимок, доказательства, риск и рекомендации. При контролируемой ошибке свежего сбора сохраняются ресурс, endpoint, выбранные правила/ключи и категория ошибки, без вымышленных обнаружений и исходного текста SDK. Некорректные аргументы/конфигурация до сбора не считаются выполненным запуском. Прерванные процессом запуски и длительные задания пока не отслеживаются — это не очередь задач.
- БД 0600, каталог 0700. Ссылка вместо БД отклоняется; SQL-параметры передаются отдельно от выражений. Тайм-аут блокировки 5 секунд; ошибки SQLite превращаются в безопасную ошибку файлового доступа. Повреждённая/неподдерживаемая БД не заменяется молча.
- ID отчётов неизменяемы: повторное сохранение того же содержимого идемпотентно, конфликт не перезаписывает историю. Максимальный канонический JSON — 32 МиБ. Отчёты и история хранятся до ручного удаления, TTL снимков остаётся 7 суток.

JsonReportRepository сохранён для старых файлов и явных локальных инструментов. Основной CLI и скрипт учебного стенда используют SQLite. `report ID` сначала ищет в БД, затем читает прежний JSON, если записи нет. Повреждённая запись БД не маскируется старым JSON.

## Схемы и идентичность

Новые SecurityReport имеют schema_version=3, ruleset_version=1 и resource_namespace. Namespace — нормализованный URL endpoint из конфигурации адаптера, не ключ и не его хеш. Он передаётся через снимок и не выводится из предположений о старых данных. Старые снимки v1/v2 и отчёты v1/v2 читаются; отсутствующая метаинформация остаётся null. Версии схем снимков не изменялись, поле namespace добавлено как необязательное.

Идентичность сравнения — mode/provider, namespace и resource.id. Сравнение одного имени на разных endpoint запрещено. Неизвестный namespace или ruleset_version не позволяет заявить об устранении. При изменении логики правил требуется повышать CURRENT_RULESET_VERSION; версия формата отчёта и версия алгоритма — разные вещи.

## CLI

```bash
# Старые файлы включаются в историю только явным импортом:
PYTHONPATH=src .venv/bin/python -m cloud_audit import-reports
# Фильтры и пагинация:
PYTHONPATH=src .venv/bin/python -m cloud_audit history --resource BUCKET_NAME --rule anonymous-read --severity high --limit 20 --offset 0
PYTHONPATH=src .venv/bin/python -m cloud_audit history --run-status failed
# Канонический отчёт либо явно отмеченное отфильтрованное представление:
PYTHONPATH=src .venv/bin/python -m cloud_audit report REPORT_ID
PYTHONPATH=src .venv/bin/python -m cloud_audit report REPORT_ID --rule anonymous-read --format markdown --output report.md
# Сравнение полной сохранённой информации:
PYTHONPATH=src .venv/bin/python -m cloud_audit compare BEFORE_ID AFTER_ID --format markdown --output comparison.md
```

history по умолчанию показывает vk; --profile demo/all позволяет отдельно смотреть учебные запуски. Фильтры --rule, --severity, --status относятся к одной и той же находке, а не к разным результатам одного запуска. --run-status: complete/incomplete/failed/demo. Severity: none/unknown/low/medium/high/critical. Limit 1–500, offset неотрицательный; total — число всех совпадений до пагинации. Сортировка по времени наблюдения (для ошибки/demo — времени записи), затем времени оценки и ID. Итоговые счётчики записи относятся к полному запуску, не обрезаются фильтром.

Фильтры report не меняют БД и не участвуют в сравнении: view_filters, is_filtered_view и full_result_count явно обозначают представление. Общий evaluation_status и код завершения исходного отчёта сохраняются. Пустое представление не означает отсутствие нарушений в полном отчёте.

--format markdown выводит самостоятельный документ с временем, namespace/версией, охватом, доказательствами, рекомендациями и проверкой исправления. --output создаёт новый файл 0600, существующий не перезаписывает. HTML и Markdown-разметка облачных строк экранируются, JSON-доказательства помещаются в ограждённые блоки. Экспорт может содержать политики/идентификаторы доступа и не предназначен для публичного распространения без просмотра владельцем.

Импорт сохраняет источники, проверяет ID/схему и не принимает отфильтрованные представления за канонические отчёты. Он идемпотентен; повреждённые или конфликтующие файлы перечисляются в skipped и дают код 3. Чтение старого JSON не импортирует его автоматически. Выбранные параметры и ошибки не содержат ключей доступа.

## Сравнение

В результате записываются контексты обоих запусков и для каждого rule_id — before/after Finding, change и reason. Это не только разница чисел.

- new: прежде passed, теперь confirmed_violation/potential_risk, есть новое наблюдение;
- persisted: находка остаётся, включая принятую исключением;
- resolved: прежде находка, теперь passed, новое время и другой снимок, та же идентичность/охват/политика/версия алгоритма;
- unchanged: passed/not_applicable остаётся таким же; это не событие исправления;
- unverified: нельзя установить переход.

Смена ресурса/namespace, набора выбранных объектов/охвата, базовой политики (кроме списка исключений), неизвестная/другая версия правил, обратное время либо ошибка уборки делают контекст несопоставимым. Пропущенное правило, insufficient_data, переход в not_applicable или отсутствие проверки ранее не считаются resolved/new. Повторная оценка одного снимка не доказывает новое нарушение или исправление. Частичный сбор посторонних настроек сам по себе не блокирует надёжную оценку конкретного правила.

Для ранее confirmed анонимного доступа требуются новые unsigned denied/HTTP 403 на всех ранее доступных точных целях, с временем позже положительных проб. Статический passed без пробы не доказывает фактическое закрытие. Мутационные пробы каждый раз используют новые ключи, поэтому отсутствие совпадающей цели не позволяет автоматически объявить устранение ранее подтверждённого write/delete. Это сознательное ограничение охвата.

comparable относится к базовому контексту; отдельные строки могут оставаться unverified. Код compare=3, если контекст несопоставим или есть unverified; 0 — все переходы классифицированы, даже если находки сохраняются. Demo и запись failed без отчёта сравнивать нельзя (код 2). История с failed не содержит фальшивого passed.
