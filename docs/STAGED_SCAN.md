# Ступенчатая проверка нескольких бакетов

## Что делает scan

`scan` — общий последовательный запуск по выбранным бакетам одного S3 endpoint. Для каждого выполняется внешний unsigned-этап и, если предоставлены ключи, внутренний анализ. Отказ List, ошибка одного бакета или неполные права не считаются отсутствием проблем и не останавливают обработку остальных целей.

Прежний `audit` сохранён для одного ресурса/снимка. Ключи в `.env` не привязываются к имени бакета. CLI автоматически читает `.env` из текущего каталога как данные, без shell; переменные процесса приоритетнее. Флаги --env-file/--no-env-file ставятся перед подкомандой.

## Выбор целей

```bash
# Несколько известных бакетов; ключи необязательны:
PYTHONPATH=src .venv/bin/python -m cloud_audit scan --buckets training-private training-public
# Все бакеты, видимые авторизованному ListBuckets:
PYTHONPATH=src .venv/bin/python -m cloud_audit scan --all-buckets
# Отдельные объекты и разрешения для каждого бакета:
PYTHONPATH=src .venv/bin/python -m cloud_audit scan --targets scan-targets.example.json
```

Ровно один источник обязателен. Без ключей endpoint не предоставляет инвентарь всех бакетов: нужен явный список/файл. Если ключи есть, но запрещён ListBuckets, явные цели всё равно проверяются; режим all сохраняет selection_status=failed с безопасной ошибкой, а не пустой успешный результат. All означает только бакеты, возвращённые данным ключом, не все хранилища провайдера.

Обрабатывается до 500 бакетов последовательно. Повторные CLI-имена удаляются с сохранением порядка; дубликаты в файле отвергаются. Файл UTF-8 JSON до 256 КиБ, поля строго ограничены. Имя — поддерживаемое DNS-имя S3 длиной 3..63, без путей. Endpoint общий; несколько endpoint проверяются отдельными запусками.

Формат файла:

```json
{
  "buckets": [
    {
      "name": "training-private",
      "objects": ["synthetic.txt"],
      "allow_mutations": false,
      "allow_residue": false,
      "policy": {"data_sensitivity": "medium", "required_controls": ["versioning"]}
    }
  ]
}
```

Объекты, политика и разрешение мутаций относятся к **этому** бакету. Секреты в файле не допускаются. `--policy PATH`, если указан, явно заменяет политику всех выбранных целей, включая файл. Новые бакеты из all получают базовую политику, без автоматического разрешения мутаций.

## Ключи и режимы

Нет обоих AWS-ключей → только внешний этап. Полная пара → оба этапа. Один/пустой второй ключ → ошибка настройки. `--external-only` явно отключает подписанный этап и игнорирует ключи окружения; `--all-buckets` с ним недопустим.

Клиент внешних запросов всегда UNSIGNED с пустыми credentials, даже когда подписанный клиент присутствует. Подписанный клиент используется для выбора бакетов, внутреннего чтения, а также подготовки/проверки эффекта/уборки искусственных мутационных целей. Успешное действие этого клиента само по себе не подтверждает анонимный доступ.

## Внешний этап

1. Анонимный ListObjectsV2, ограниченное перечисление страниц.
2. GET Range bytes=0-0 известных и найденных объектов; Body читается максимум на один байт и закрывается, не сохраняется.
3. При явном разрешении — независимые Write и Delete на разных новых `_cloud-audit-probe/UUID/*.txt`.

Get известных файлов выполняется даже при запрещённом List. Нет списка и известных ключей → чтение не проверено; общий результат неполный, не «всё закрыто». 403 означает отказ конкретному запросу, 404 не доказывает безопасность или отсутствие бакета. Разрешённый List сам по себе уже доказательство раскрытия списка, даже если поздняя страница завершилась ошибкой; охват списка при этом failed/limited.

`--max-objects N` — 1..20, по умолчанию 20. В одном бакете максимум 20 запросов страниц, до N уникальных ключей. Известные ключи приоритетны; объединение внешнего/внутреннего списка также ограничено N. Если что-то не вошло, охват limited. Все объекты/версии автоматически не сканируются, а содержимое найденных файлов не выгружается.

## Запись и удаление

```bash
# С ключами подготовки и уборки — только для перечисленных учебных бакетов:
PYTHONPATH=src .venv/bin/python -m cloud_audit scan --targets scan-targets.example.json --mutation-buckets training-public
# Совсем без ключей: явное принятие возможных оставшихся искусственных объектов:
PYTHONPATH=src .venv/bin/python -m cloud_audit scan --buckets training-public --external-only --mutation-buckets training-public --allow-residue
```

Альтернатива CLI — allow_mutations=true для конкретной строки файла. Без ключей дополнительно нужен allow_residue=true для этой строки. Глобальный --allow-residue применяется только вместе с явным --mutation-buckets. Указание бакета вне выбранного набора отклоняется. Обнаружение бакета через all само по себе записи не разрешает.

**Write:** unsigned PUT искусственного тела и метки по новому UUID-ключу, с IfNoneMatch='*'. Успешный 2xx подтверждает принятие загрузки, даже если уборка затем не удалась. Не трогает известные/найденные пользовательские ключи.

**Delete:** отдельный искусственный объект подготавливается подписанным клиентом либо анонимной загрузкой. Требуются успешное создание, HEAD до удаления и HEAD после unsigned DELETE. Только наличие до и подтверждённый 404 объекта после дают allowed/current_object_absent. Один DELETE 204 без этого — unverified. При версионировании это подтверждает исчезновение текущей версии из обычного доступа, а не физическое уничтожение всей истории. Отказ Write не означает отказ Delete: с ключами подготовка второго объекта независима.

С подписанным клиентом заранее проверяются версионирование, отсутствие Object Lock и пустота точного probe-ключа в списке версий. Неизвестность или существующая цель → not_tested с причиной, без попытки записи/удаления этой цели.

**Уборка:** удаляются только версии точного probe-ключа с совпадающей уникальной меткой и известные маркеры удаления. Имена metadata-заголовков сопоставляются без учёта регистра. Чужие версии/ключи не удаляются. При подтверждённо выключенном версионировании текущая null-версия проверяется/удаляется обычным HEAD/DELETE; для остальных версий требуется доступ к операциям с версиями. После удаления проверяются оставшиеся версии и отсутствие текущей цели. Уборка не считается успешной на одном HTTP-ответе.

Без ключей утилита пробует анонимную уборку собственных подтверждённо созданных целей, но не может подтвердить удаление всех версий. Поэтому сохраняет cleanup=residue/unknown и точный ключ, даже если DELETE вернул 2xx. Возможность остатка принимается **до** сетевых мутаций; это отражается в сводке и коде 3. Неизвестный исход PUT также не выдаётся за гарантированное отсутствие остатка.

## Внутренний этап

Независимо от внешнего результата:

1. Подписанное ограниченное перечисление объектов.
2. Дополнительные unsigned GET новых найденных ключей, без повторного List/Write/Delete.
3. Сбор восьми настроек и ACL выбранных объектов.
4. Сохранение нового обогащённого снимка с фактами внешнего этапа и пересчитанной полнотой; старый ID не перезаписывается.
5. Выполнение существующих восьми правил и сохранение обычного SecurityReport v3 в SQLite.

Если список объектов недоступен, известные объекты и доступные настройки всё равно анализируются. Недоступные источники остаются insufficient_data/ограничениями. Ошибка внутреннего анализа сохраняется в общей сводке; внешние доказательства не теряются. Внешний режим без ключей не придумывает результаты настроек, которые не читал.

Алгоритмы восьми правил описаны в [SCANNING.md](SCANNING.md). Внешняя оценка использует те же четыре anonymous-ID и модель риска для конкретных проб, не добавляя четыре новых правила в реестр. Исключения и требуемые права применяются обычным внутренним движком; внешние факты о реально доступной операции остаются видимыми.

## Результаты и хранение

```bash
PYTHONPATH=src .venv/bin/python -m cloud_audit scan --targets scan-targets.example.json --format markdown --output staged-report.md
PYTHONPATH=src .venv/bin/python -m cloud_audit scan-report SCAN_ID --format markdown
PYTHONPATH=src .venv/bin/python -m cloud_audit report INTERNAL_REPORT_ID
```

Сводка показывает List/Get/Write/Delete отдельно от внутреннего статуса и ссылки на отчёт. Для каждого бакета сохранены исходный ScanTarget, пробы (outcome/HTTP/время/эффект/подготовка/уборка), внешние находки/рекомендации, охват двух списков, ошибки и ограничения.

Общие сводки: STATE_DIR/data/scans/SCAN_ID.json, каталог 0700, атомарный файл 0600 без перезаписи, schema_version=1, максимум 32 МиБ. Чтение проверяет типы, версии, статусы и согласованность риска/выводов с пробами. Это не криптографическое подтверждение локального файла. Ключей и содержимого файлов в сводке нет. SQL-схема прежней истории не менялась; внутренние отчёты доступны через report/history/compare, общая сводка — через scan-report. Статусы внутренних failed хранятся в общей сводке без фиктивного успешного отчёта.

Код 0 — выполнены выбранные операции/охват, не гарантия безопасности всего хранилища. Код 3 — неполный выбор/охват/этап/уборка; нарушения сами по себе не меняют код. Намеренно выключенные мутации отображаются как not_tested и не считаются проверенными; их внешняя находка insufficient_data не делает остальные выбранные операции невыполненными. Код 2 — ошибка аргументов/конфигурации/чтения сводки, код 1 — локальное состояние/экспорт.

## Проверка реализации

Новые тесты: `PYTHONPATH=src .venv/bin/python -m unittest discover -s tests -p 'test_staged_*.py' -v`.

Изолированный реальный стенд: `PYTHONPATH=src .venv/bin/python scripts/verify_staged_scan.py --run-training-fixture`. Создаёт только новые три бакета с искусственными данными, включает public Write/Delete только для своего probe-префикса, проверяет внешний режим без ключей и закрытие, удаляет все созданные объекты/версии/бакеты в finally. Для него нужны права создания и уборки стенда сверх обычных прав аудитора. Свои существующие бакеты он не изменяет.

Статус и фактические артефакты испытаний — в [ITERATION_11.md](ITERATION_11.md). ИИ перенесён на итерацию 12.
