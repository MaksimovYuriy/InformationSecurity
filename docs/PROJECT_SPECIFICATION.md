# Описание проекта и технические спецификации

Этот документ — основной источник технического контекста перед выполнением задач. Он описывает актуальную реализацию, контракты и принятые технические решения. Обновляется вместе с изменениями кода и спецификаций. Планы будущих возможностей явно отделяются от работающего поведения.

## Назначение и состояние

Цель — служба проверки безопасности облачного хранилища: получение конфигурации, выполнение 6–10 правил, оценка опасности, рекомендации и подтверждение исправлений. ИИ-агент входит в проект и добавляется последним.

Завершены итерации 1 и 2: локальное окружение и консольный сценарий на фиксированных демонстрационных данных. Для итерации 3 выбран VK Cloud Object Storage (S3), московский endpoint `https://hb.ru-msk.vkcloud-storage.ru`. По сообщению пользователя созданы учебный бакет, тестовые файлы и учётные данные; 22.11.2026 реальными CLI-запусками подтверждены подключение и получение одного бакета. Итерация 3 принята пользователем как завершённая с явно согласованным исключением: минимальность прав аудитора и отдельное сопоставление списка с кабинетом не подтверждены и не блокируют дальнейшую разработку. Эти проверки не считаются выполненными. Итерация 4 завершена: реализованы сбор и нормализация настроек бакета, безопасное сохранение и чтение снимков; реальный запуск проверен. Итерация 5 завершена: реализованы движок правил, контекст/исключения, модель риска и первая реальная проверка версионирования. На учебном бакете получено Enabled → passed; отчёт и повторный анализ снимка проверены. Итерация 6 завершена: добавлены четыре правила анонимного доступа, анализ поддерживаемой части политик/ACL, выбранные ACL объектов и unsigned-пробы. Реальный изолированный сценарий «закрыто → открыто → закрыто» прошёл, созданный временный стенд удалён. Condition/Not* пока не вычисляются и отражаются как ограничения. Итерация 7 завершена: окончательный набор из восьми правил зафиксирован в docs/rules/RULE_CATALOG.md. Добавлены внешний именованный доступ, избыточные явные права и рекомендация отключения ACL; контекст желаемых разрешений не выдумывается. Реальный запуск подтвердил анонимное чтение выбранного учебного объекта, при закрытом списке; без модели необходимых прав оценка избыточности остаётся insufficient_data. Итерация 8 завершена: SQLite, история с фильтрами, JSON/Markdown, импорт прежних отчётов и сравнение по ресурсу, охвату и версии правил. Реальный повторный аудит подтвердил устранение анонимного read/list; ошибка запроса не создаёт ложного исправления. Отдельная VM потребуется при серверном развёртывании в итерации 9.

## Стек и запуск

- Python 3.12+, boto3 1.35.99 для облачного профиля. Проверенный набор прямых и транзитивных зависимостей закреплён в `requirements.txt`; установка: `.venv/bin/python -m pip install -r requirements.txt`.
- Исходники в `src`, тесты — `unittest` в `tests`.
- Версия приложения: `0.1.0`, определена в `src/cloud_audit/__init__.py` и метаданных `pyproject.toml`.
- Проверенный способ запуска из корня: `PYTHONPATH=src .venv/bin/python -m cloud_audit ...`.
- Установочная консольная точка входа в метаданных: `cloud-audit = cloud_audit.cli:main`; установка пакета не входит в выполненные проверки.

`StorageProvider` также задаёт `mode`, `audit_available` и `connection_message`; сервис не привязан к demo. Прежний `AuditService.audit` обслуживает demo; его защита от имитации облачного аудита сохранена. CLI направляет настоящий аудит VK Cloud в `SecurityAuditService` с `RuleEngine`. Интерфейс `preview` остаётся только демонстрационным каркасом.

## Модели данных

- `Settings`: `environment: str`, `log_level: str`, `state_dir: Path`.
- `Resource`: `id: str`, `name: str`.
- `RuleResult`: `rule_id: str`, `status: str`, `explanation: str`.
- `AuditReport`: `id: str`, `mode: str`, `resource: Resource`, `results: tuple[RuleResult, ...]`.
- `EnvironmentReport`: `status: str`, `environment: str`, `log_level: str`.

При JSON-сериализации кортеж результатов становится массивом. Идентификатор отчёта — `uuid4().hex`: 32 шестнадцатеричных символа в нижнем регистре. Время, риск и доказательства отсутствуют в прежнем demo-AuditReport; для настоящего аудита введена отдельная модель SecurityReport версии 1 (см. ниже).

## Контракт CLI

| Команда | Параметры и поведение |
|---|---|
| `--version` | Версия без подготовки каталогов |
| `check` | Подготовка окружения; JSON с `version`, `status`, `environment`, `log_level` |
| `connection` | demo: имитация; vk: авторизованный ListBuckets |
| `resources` | demo: фиксированные ресурсы; vk: реальные бакеты с пагинацией |
| `audit` | Ровно один из `--resource`/`--snapshot`; необязательные `--rules` и `--policy PATH`; для свежего vk доступны `--objects`, `--probe-anonymous`, `--allow-write-probes`; demo допускает только ресурс |
| `report REPORT_ID` | Чтение отчёта; фильтры `--rule`, `--severity`, `--status` |
| `history` | История: `--resource`, `--rule`, `--severity`, `--status`, `--profile vk/demo/all`, `--run-status`, `--limit`, `--offset` |
| `compare BEFORE_ID AFTER_ID` | Сравнение полных сохранённых настоящих отчётов |
| `import-reports` | Явный идемпотентный импорт прежних JSON в SQLite, источники сохраняются |
| `collect` | Обязательный `--resource`, профиль только `vk` (по умолчанию); сбор и сохранение конфигурации одного бакета |
| `snapshot SNAPSHOT_ID` | Чтение сохранённой конфигурации без облачных ключей и сетевых запросов |

Для `connection`, `resources`, `audit` доступен `--profile demo|vk`, значение по умолчанию — `demo`. Облачный `audit --profile vk` выполняет выбранные реальные правила (сейчас восемь); по умолчанию — все зарегистрированные. `--snapshot` и `--policy` требуют vk. Офлайн-анализ снимка не требует ключей и не создаёт SDK-клиент. Для подкоманд просмотра/аудита доступен `--format json|text`, по умолчанию `json`; report/history/compare также поддерживают markdown и `--output PATH` (новый файл 0600 без перезаписи). Текстовый формат — заголовок DEMO либо VK CLOUD согласно режиму и форматированный JSON. Для `connection`/`resources` заголовок VK сообщает об отсутствии оценки безопасности. Для collect/snapshot также обозначен охват конфигурации бакета. Настоящий audit/report имеют заголовок о выбранных проверках и ограничениях, без общего заявления о безопасности бакета.

Демонстрационные ресурсы: `demo-public` и `demo-private`. Единственный сценарий — `demo-public-read`, он выбирается при отсутствии `--rules`. Неизвестные сценарии отклоняются, повторы исключаются. Результат всегда имеет статус `simulated`, а отчёт — `mode: demo`: это не заключение о безопасности.

Коды завершения:

- `0`: команда выполнена; для снимков — все запрошенные настройки доступны либо явно отсутствуют (`complete_for_scope`). Не означает отсутствие нарушений.
- `1`: ошибка доступа к локальному состоянию.
- `2`: неверные аргументы, конфигурация, ресурс, правило, идентификатор или недоступный/некорректный отчёт; ошибка облачной авторизации, доступа, сети, API или ответа.

Ошибки выводятся в stderr без traceback для предусмотренных случаев. Код `3`: для collect/snapshot — частичный снимок; для настоящих audit/report — evaluation_status=incomplete (хотя бы одно insufficient_data либо probe_cleanup_failed). Нарушение или принятое исключение сами по себе не меняют код 0; он означает выполнение выбранных правил. Частичность сбора указывается отдельно и не мешает complete-оценке правила, если необходимые ему данные доступны.

Все команды после разбора аргументов, кроме `--version` и справки, подготавливают каталоги состояния.

## Конфигурация и безопасность

| Переменная | По умолчанию | Допустимые значения |
|---|---|---|
| `CLOUD_AUDIT_ENV` | `development` | `development`, `test`, `production` |
| `CLOUD_AUDIT_LOG_LEVEL` | `INFO` | `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL` |
| `CLOUD_AUDIT_STATE_DIR` | `.state` | Непустой путь к выделенному каталогу приложения |

Приложение читает окружение процесса, автоматически `.env` не загружает. Инструкция доверенной загрузки через shell — в README. `.env.example` содержит только безопасные значения; `.env` и его варианты исключены из Git.

Для `--profile vk` используются `CLOUD_AUDIT_S3_ENDPOINT_URL` (по умолчанию `https://hb.ru-msk.vkcloud-storage.ru`), `CLOUD_AUDIT_S3_REGION` (регион подписи, по умолчанию `us-east-1`), обязательные `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY`. Ключи исключены из repr модели `S3Settings`. Endpoint должен быть HTTPS без credentials, query, fragment и пути (кроме `/`), порт 443 или не указан. Учётные данные передаются SDK явно; не выполняется поиск ключей через metadata или профили AWS. Файл `.env` автоматически не читается; при проверке значения загружались вспомогательным процессом локально и не выводились агенту.

Конфигурация подключения общая для нескольких бакетов, имя бакета в окружении не задаётся. Целевой ресурс выбирается `audit --resource` либо из сохранённого снимка через `audit --snapshot`. Пакетный аудит всех бакетов также не реализован.

SDK использует Signature V4, path-style, тайм-ауты 5/10 секунд и до трёх попыток в standard mode. `ListBuckets` вызывается без фильтра по имени, continuation token обрабатывается до конца, дубликаты удаляются, ошибочная пагинация отклоняется. Неполный результат при ошибке не возвращается. Отказ доступа не превращается в пустой список. Сообщения SDK не выводятся, SDK-логгеры ограничены уровнем CRITICAL даже при DEBUG приложения. По умолчанию адаптер не выполняет операций записи. Только явно включённые --allow-write-probes вместе с --probe-anonymous создают/удаляют новые временные объекты для проверки, с подготовкой и уборкой через отдельный подписанный клиент. Скрипт изолированного стенда также явно создаёт новый бакет и искусственный файл. Успешное подключение не доказывает отсутствие прав записи у ключа.

Каталоги состояния, `data` и `logs` создаются с правами `0700`; у существующих этих каталогов права также изменяются на `0700`. Проверяется возможность записи. Нельзя указывать общий каталог пользователя как корень состояния.

Новые отчёты и история хранятся в `STATE_DIR/data/audit.sqlite3` (0600), SQLite из стандартной библиотеки, user_version=1. Таблицы runs/run_rules сохраняют полный канонический JSON, параметры, времена, результаты и индексируемые поля; запись выполняется транзакционно. ID неизменяем: идентичное сохранение идемпотентно, конфликт отклоняется. Проверяется схема отчёта, размер ограничен 32 МиБ. Повреждённая БД и неизвестная версия не маскируются пустой историей. Контролируемая ошибка свежего облачного аудита записывается отдельным failed-run с выбранными правилами/охватом/namespace и безопасным кодом ошибки, без находок; аварийное завершение процесса не отслеживается.

Прежние `STATE_DIR/data/REPORT_ID.json` доступны через fallback при отсутствии ID в БД; `import-reports` явно включает их в историю, не удаляя источники. Demo без версии и SecurityReport v1/v2 читаются совместимо; новые настоящие отчёты имеют schema_version=3, ruleset_version="1" и resource_namespace (нормализованный endpoint). Namespace переносится из нового снимка; для старых снимков он неизвестен, а не берётся из текущего окружения. Снимки v1/v2 совместимы с необязательным resource_namespace. Версию правил необходимо повышать при изменении их смысла. Проверяются ID, режим, структура, пять статусов, доказательства, согласованность риска и evaluation_status; confirmed_violation анонимных правил требует положительной unsigned-пробы HTTP 2xx. Это проверка согласованности, не криптографическая подлинность. Ключи не включаются; автоматического TTL отчётов пока нет.

Логирование — стандартный `logging` в stderr. Секреты запрещены в коде, Git, журналах, отчётах и контексте ИИ.


## Снимок конфигурации v1 — итерация 4

Базовый формат v1 (сохранён для обратной совместимости; расширение v2 описано ниже). `ConfigurationSnapshot`: `id` (uuid4 hex), `schema_version: 1`, `provider`, `resource`, `collected_at` (ISO 8601 с UTC, начало сбора), `scope: bucket_configuration_only`, `limitations`, `collection_status` и кортеж `observations`. `ConfigurationObservation`: `name`, `source` (исходный метод API), `status`, `data` (нормализованный JSON-словарь либо `null`), `reason` (безопасная причина либо `null`).

Собираются восемь настроек: `bucket_acl`, `bucket_policy`, `public_access_block`, `ownership_controls`, `versioning`, `logging`, `encryption`, `object_lock`. В ACL хранятся идентификатор владельца и гранты (тип/идентификатор субъекта/разрешение); политика сохраняется JSON-документом с исходными условиями без интерпретации. Остальные настройки нормализуются в независимые словари с именами полей snake_case. Неизвестный MFADelete — `null`; отсутствие Status в успешном GetBucketVersioning означает Disabled согласно контракту S3. Снимки могут включать идентификаторы, ARN и политику ресурса; ключи и SDK ResponseMetadata в них не включаются.

Статусы данных: `available`, `absent`, `access_denied`, `unsupported`, `error`. Отсутствующая настройка определяется только специальным кодом API либо документированным успешным пустым ответом. Неоднозначный 404 остаётся ошибкой, NoSuchBucket прерывает сбор. Ошибки авторизации также прерывают сбор без записи. Остальные ошибки фиксируются в соответствующем поле, остальные настройки продолжают собираться. `complete_for_scope` устанавливается только при available/absent для всех восьми настроек; иначе `partial`. Это статусы сбора данных, а не будущие статусы нарушений.

Охват: только настройки конкретного бакета, прямые Get-запросы без ListObjects и GetObject. ACL объектов, содержимое файлов и настройки аккаунта не собираются; запросы последовательны, атомарность состояния облака не гарантируется. Ограничения всегда включают `object_acl_not_collected`, `object_contents_not_collected`, `account_controls_not_collected`, `security_not_assessed`, `sequential_requests_not_atomic`. Неприменимость объектных проверок этому режиму отражена охватом, а не результатами о безопасности объектов.

Хранение: `STATE_DIR/data/snapshots/ID.json`, каталог 0700, файлы 0600, временный файл + fsync + атомарная замена. Максимум 2 МиБ; при чтении и сохранении проверяются идентификатор, версия, структура, источники, статусы, формы данных и согласованность полноты. Символические ссылки на файлы отклоняются. Дата более чем на 5 минут в будущем отклоняется, чтобы не обходить срок хранения. Срок — 7 суток от начала сбора: просроченные снимки не выдаются, корректные просроченные файлы удаляются при следующем сохранении. Фонового удаления нет; повреждённые/посторонние файлы не удаляются автоматически. CLI snapshot работает без ключей. Подробные поля и сценарии — в `docs/ITERATION_04.md`.


## Движок правил и модель риска — итерация 5

`SecurityRule` определяет `id`, `required_data`, `applicable`, `evaluate`, `recommendation`, `verification`. `RuleEngine` получает реестр через конструктор, отклоняет повторные ID и неизвестный выбор, исключает повторы выбранных правил. Неприменимость проверяется до входных данных. Известное отсутствие настройки передаётся правилу для интерпретации; missing/access_denied/unsupported/error в требуемых наблюдениях дают insufficient_data. Неподдерживаемые API, не нужные выбранному правилу, не препятствуют его оценке.

Статусы Finding: confirmed_violation, potential_risk, passed, insufficient_data, not_applicable. Доказательство Evidence содержит field/source/observation_status/value; Finding — также explanation, RiskAssessment, recommendation, verification, exception_reason. Исключение применимо только к нарушениям/потенциальным рискам: сохраняет исходный статус, риск и доказательства, добавляя причину. Истёкшее исключение или исключение для другого ресурса не применяется; недостаток данных не подавляется.

AuditPolicy загружается через `--policy` из JSON до 64 КиБ; пример — `audit-policy.example.json`. Поля: data_sensitivity (unknown/low/medium/high), required_controls (versioning и acl_disabled; по умолчанию требуется только versioning), allowed_external_accounts (список строк), required_permissions (subject и список operations: read/list/write/delete/read_acl/write_acl/read_policy), exceptions (точные resource_id/rule_id, непустая reason, необязательная expires_at с часовым поясом). Некорректные типы/неизвестные поля и повторные пары исключений отклоняются без вывода значений. Списки аккаунтов и необходимых прав не используются правилом версионирования; начиная с итерации 7 они используются отдельными правилами явного внешнего доступа и избыточности. Дополнительное необязательное поле trusted_project_ids задаёт собственные/доверенные проекты. Эти поля не являются доказательством фактического входа субъекта.

Первое правило — bucket-versioning-enabled: Enabled → passed; Disabled/Suspended → confirmed_violation при обязательной мере versioning, иначе potential_risk. Подтверждается несоответствие заданной базовой политике, а не фактическая потеря данных. Неизвестное значение/недоступность → insufficient_data. Карточка, угрозы, исключения и рекомендации — `docs/rules/BUCKET_VERSIONING.md`. Аудитор не меняет настройки облака.

RiskModel v1: экспертный порядковый score=likelihood×impact. Impact 1/2/3 для low/medium/high чувствительности, при unknown условно 2 с явной оговоркой. Likelihood 3 при подтверждённой публичной доступности, иначе условно 2; первое правило всегда использует неизвестную доступность, не анализируя фактические права. Уровни 1–2 low, 3–4 medium, 6 high, 9 critical. Для passed/not_applicable — none и 0; для insufficient_data — unknown и null. affected_operations описывает механизм возможного ущерба; только положительная unsigned-проба подтверждает конкретную операцию на записанной цели, что отдельно указано в rationale. Модель не даёт статистическую вероятность, не подтверждает резервные копии и фактическую возможность восстановления. Подробная методика — в `docs/ITERATION_05.md`.

Исходный SecurityReport v1 (итерация 5, чтение сохранено) содержит id, mode=vk, resource, snapshot_id, snapshot_collected_at, evaluated_at, scope, limitations, collection_status, evaluation_status, policy, results. Отчёт хранит необходимые доказательства и контекст, поэтому читается и после истечения срока входного снимка. Для повторного анализа через --snapshot нужен непросроченный снимок. Ограничения исходного снимка сохраняются, кроме security_not_assessed, который заменяется на only_selected_rules_evaluated. Оценка complete не означает отсутствия обнаружений или актуальности конфигурации после времени сбора. История и сравнение реализованы в итерации 8 (см. ниже). Анализ публичного доступа добавлен в итерации 6 в указанном ниже ограниченном объёме.


## Публичный доступ и схема v2 — итерация 6

В итерации 6 реестр был расширен до bucket-versioning-enabled и anonymous-read/list/write/delete; в итерации 7 добавлены три правила управления доступом (см. ниже). PublicAccessRule не требует заранее полной доступности всех источников: положительная runtime-проба может подтвердить доступ даже при неполной конфигурации. Для статического анализа рассматриваются подходящие Action/Resource/Principal и безусловные Deny, политики и релевантные ACL. Bucket READ в VK Cloud означает список, object READ — содержимое; bucket WRITE — загрузку и удаление, object FULL_CONTROL не означает удаление. AuthenticatedUsers не считается анонимным AllUsers. BucketOwnerEnforced отключает ACL, доступный IgnorePublicAcls учитывается. Известный безусловный Deny приоритетнее Allow и ACL.

Поддержаны строки/списки и маски * и ? (не shell-классы []); Action без учёта регистра, Resource с учётом. Condition и Not* не вычисляются: возвращается ограничение policy_data_or_conditions_not_resolved. Неизвестные источники/условия не дают уверенного passed. Публичное разрешение в конфигурации — potential_risk, положительная unsigned-проба — confirmed_violation. Недостаточные данные — insufficient_data; passed ограничен выбранными целями и поддерживаемой моделью. Отрицательная проба не отменяет возможный доступ в другом контексте. Риск положительной пробы использует likelihood=3. Карточки — docs/rules/ANONYMOUS_ACCESS.md.

CollectionOptions содержит до 20 уникальных object_keys, probe_anonymous и allow_write_probes. Для collect и свежего audit доступны --objects KEY ... и --probe-anonymous; для demo и --snapshot эти флаги отклоняются. По умолчанию проб нет. GetObjectAcl выполняется только для явно выбранных ключей, без обхода всех объектов. Отсутствующий объект имеет статус not_found/resource_not_found, отличный от access_denied.

Если переданы расширенные опции, создаётся снимок v2 с object_keys и scope=bucket_and_selected_objects при непустом выборе, иначе bucket_configuration_only. Восемь базовых наблюдений сохраняются, добавляются object_acl:KEY и при включении проб anonymous_list, anonymous_read:KEY, при мутациях anonymous_write/delete. Форма данных, имена/источники, статусы и выбор проверяются при чтении. В v2 ограничения явно указывают only_selected_objects_collected либо object_acl_not_collected, object_contents_not_stored, account_controls_not_collected, security_not_assessed и sequential_requests_not_atomic. Старые v1 читаются. Семидневное хранение и приватные атомарные файлы сохранены.

Unsigned-клиент имеет отдельную сессию с signature_version=UNSIGNED; авторизация и credential-параметры не отправляются. ListObjectsV2 ограничен MaxKeys=1, GetObject — Range bytes=0-0 с чтением максимум одного байта и закрытием потока. Ответы содержимого и список имён не сохраняются. Метаданные пробы: outcome (allowed/denied/not_found/error), http_status, checked_at и object_key при необходимости. 403 AccessDenied — отказ конкретному запросу, 404/сеть/некорректный ответ не являются доказательством запрета. Ошибка пробы делает снимок partial.

Запись/удаление требуют --allow-write-probes вместе с --probe-anonymous, подтверждённого отсутствия Object Lock и доступа подготовки/уборки. Создаются только новые ключи _cloud-audit-probe/UUID/write.txt или delete.txt, с условием IfNoneMatch=*. Существующие версии проверяются до операции и не трогаются. Для удаления предварительно создаётся искусственный объект. Уборка перечисляет и удаляет только версии/маркеры точного временного ключа. Ошибка уборки сохраняет успешное доказательство, но отмечает cleanup_failed/probe_cleanup_failed и incomplete. В реальном облаке положительные публичные write/delete не включались; механизм проверен локальными сценариями.

В итерации 6 SecurityReport получили schema_version=2, object_keys и limitations у каждого Finding. Нормализованные входные настройки и метаданные проб сохраняются в evidence.value как JSON-строка; исходное содержимое файлов не включается. Общий отчёт агрегирует ограничения и отмечает only_selected_rules_evaluated. Для write/delete отдельно указан охват генерируемых временных объектов; отсутствие конкретной пробы не скрывается наличием других проб. Старые отчёты v1 читаются; --snapshot повторно оценивает сохранённые факты, не запускает сеть.

Изолированный воспроизводимый сценарий: PYTHONPATH=src .venv/bin/python scripts/verify_public_access.py --run-training-fixture. Он создаёт новый бакет и константный искусственный файл, проверяет private, кратковременно разрешает read/list через политику, удаляет политику и подтверждает отказ; finally закрывает и удаляет созданные ресурсы. Публичную запись не включает, существующий пользовательский бакет не изменяет. Сводка записывается в .state/data/fixture-UUID.json с правами 0600. Протокол — docs/ITERATION_06.md.


## Окончательный набор и контекст управления доступом — итерация 7

Зарегистрированы восемь правил: bucket-versioning-enabled, anonymous-read, anonymous-list, anonymous-write, anonymous-delete, unapproved-external-access, excess-explicit-permissions, bucket-acl-disabled. Обоснование, источники, алгоритм, риск, исключения, рекомендации и подтверждение — в docs/rules/RULE_CATALOG.md и связанных карточках. Журналирование/шифрование не включены в обязательный набор из-за неподдерживаемых API стенда; HTTPS endpoint не подменяет проверку запрета незащищённого транспорта. SDK-сбор и схемы снимков в итерации 7 не расширялись.

Новые правила используют доменный инвентарь явных Allow/Deny и ACL в выбранном охвате. Разворачиваются GetObject/ListBucket/PutObject/DeleteObject/GetBucketAcl/GetObjectAcl/PutBucketAcl/PutObjectAcl/GetBucketPolicy в операции read/list/write/delete/read_acl/write_acl/read_policy. Маски раскрываются только в этой конечной модели и отмечаются неполнотой, неизвестные действия/условия/Not* и формы Principal не дают уверенного passed. Безусловный Deny учитывается по субъекту/операции/ресурсу. Проектный грант покрывает user ARN проекта; запрет одному пользователю не отменяет доступ всего проекта, но применяется при проверке его baseline. Права AuthenticatedUsers учитываются для выбранных аутентифицированных субъектов. BucketOwnerEnforced отключает ACL, IgnorePublicAcls игнорирует публичные группы, а не именованные CanonicalUser-гранты.

AuditPolicy дополнена trusted_project_ids (необязательный список строк). allowed_external_accounts допускает точный субъект или проект и его user ARN. Владелец бакета доверенный по метаданным ACL; владелец произвольного объекта не считается автоматически доверенным для всего бакета. unapproved-external-access возвращает potential_risk для неутверждённых внешних явных грантов; без контекста своего проекта для named-политик — insufficient_data. Principal * и AllUsers остаются отдельными анонимными проверками. Passed ограничен явными грантами выбранных ресурсов и не означает полного отсутствия внешнего доступа.

excess-explicit-permissions сравнивает наблюдаемые операции настроенных субъектов с required_permissions. Пустой список baseline целиком, ненаблюдаемый субъект, неизвестный собственный проект или неучтённые неявные внутренние права не дают утверждения о least privilege. Видимое превышение — potential_risk, иначе при неполноте insufficient_data. Одна запись baseline на subject, повторы отклоняются. Явный пустой operations означает, что субъекту не нужны никакие операции; это отличается от отсутствия baseline. Текущие права не копируются автоматически в желаемые. Внутренние роли/implicit allow, полный IAM, неподдерживаемые действия, все объекты и версии не анализируются.

bucket-acl-disabled: BucketOwnerEnforced → passed; Preferred/ObjectWriter → potential_risk, а при требовании acl_disabled — confirmed_violation базовой политики; неизвестность → insufficient_data. Это мера против случайного открытия через ACL, не гарантия отсутствия публичных политик. Рекомендация требует проверки совместимости приложений, изменений аудитор не делает. При чтении отчёта проверяется соответствие результата значению Ownership Controls и baseline.

Новые поля политики сохраняются в отчётах v2; старые v1/v2 без trusted_project_ids читаются с пустым значением. Версия снимков не менялась. Риск и исключения используют существующие механизмы; named-гранты не выдаются за подтверждённые сеансы доступа. Реальный аудит всех восьми правил и повторный офлайн-анализ новых правил подтверждены. На выбранном учебном объекте unsigned-чтение успешно (confirmed_violation/high), unsigned-список закрыт. Включённые ACL дают potential_risk; отсутствие пользовательской baseline даёт insufficient_data для избыточности. Облако в этой итерации не изменялось. Протокол — docs/ITERATION_07.md.

## История, экспорт и сравнение — итерация 8

История по умолчанию показывает vk; demo/all выбираются явно. Фильтры правила/опасности/статуса совпадают в одной находке, счётчики записи относятся ко всему запуску. Пагинация limit=1..500 (по умолчанию 50), offset≥0, total до пагинации; сортировка по времени наблюдения, затем оценки и ID. Для failed/demo используется время записи. Статусы запуска: complete/incomplete/failed/demo. Report-фильтры создают явно маркированное представление (is_filtered_view, view_filters, full_result_count), не меняют данные или исходный evaluation_status. Markdown включает время, контекст, доказательства, риск, рекомендации и способ подтверждения; облачные строки экранируются. Локальные команды не создают SDK и не требуют ключей.

Сравнение возвращает оба полных контекста и для каждого rule_id before/after, change и reason. Идентичность включает mode, resource.id и известный одинаковый namespace; также требуются одинаковые охват/выбранные объекты, базовая политика (исключения не скрывают находку) и известная версия правил. Смена контекста, обратное время или probe_cleanup_failed дают unverified. Пропущенное правило, insufficient_data и переход в not_applicable не считаются устранением. New: passed→находка; persisted: находка остаётся; resolved: находка→passed; unchanged: одинаковые passed/not_applicable. Для new/resolved нужен другой снимок с более поздним наблюдением. Для ранее подтверждённой анонимной операции resolved дополнительно требует новой unsigned denied/HTTP403 на всех ранее доступных точных целях; статического passed недостаточно. Генерируемые write/delete-цели могут не совпасть, тогда исправление не подтверждено. Старые отчёты без namespace/версии не получают выдуманной сопоставимости.

Код compare=3 при несопоставимости или любом unverified, иначе 0; demo/failed без отчёта дают 2. Import со skipped даёт 3. Ошибка получения данных не создаёт passed. Протокол, команды и ограничения: `docs/ITERATION_08.md`.
