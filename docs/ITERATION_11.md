# Итерация 11: ступенчатая обработка нескольких бакетов

## Статус

Завершена. Реализованы scan/scan-report, три способа выбора целей, независимые внешний/внутренний этапы, ограниченный поиск объектов, явно разрешённые Write/Delete, общая сводка и отдельные внутренние отчёты. ИИ перенесён на итерацию 12.

## Облачный стенд, 22.11.2026

Команда `scripts/verify_staged_scan.py --run-training-fixture` создала три новых бакета с уникальным префиксом, каждый с `synthetic-staged-fixture.txt`:

1. closed — без публичных разрешений;
2. public — List/Get и Write/Delete только искусственного probe-префикса;
3. object — один публичный объект через ACL при запрещённом списке.

Все файлы искусственные, существующий пользовательский бакет не изменялся. Ключи локально загружены вспомогательным процессом и не выводились. Успех сценария: **success=true, cleanup_ok=true**, 7 запусков scan, **44,167 с** включая подготовку/паузы/уборку. Все три бакета, версии и маркеры удалены.

Артефакт: `.state/data/staged-fixture-eb8b3b0fb162403e8189c7d5c4c80bd0.json`.

Публичный объект при закрытом List у третьего бакета подтверждён во всех публичных попытках. Закрытый первый бакет доступа не дал.

### Что означает объединение доказательств

После смены политики запросы к public-бакету дали неодинаковые исходы между попытками. Причина на стороне провайдера отдельно не установлена. Доказательство существования публичной операции — конкретный успешный unsigned-запрос; оно не требует, чтобы четыре разных операции одновременно разрешились в одном запуске.

Стенд принимает публичную фазу по набору исходных положительных свидетельств ограниченных попыток. Для Write/Delete дополнительно требуется подтверждённая уборка, для Delete — current_object_absent. **Объединённый фиктивный ScanRun не создаётся**: каждая сводка, HTTP-исход и ID остаются отдельными. Отказы не заменяются на allowed, нестабильность не скрывается. Закрытие проверяется новой отдельной серией с отрицательными исходами.

### Что было исправлено по реальному запуску

Ранний запуск остановился на неопределённой уборке; общий finally успешно удалил весь стенд. Диагностика собственного искусственного объекта показала, что VK возвращает metadata как `Cloud-Audit-Probe`; теперь имя заголовка сопоставляется без учёта регистра. Для текущей null-версии при подтверждённо выключенном версионировании применяются обычные HEAD/DELETE, остальные версии по-прежнему обрабатываются по VersionId и метке. Отдельные тесты подтверждают, что чужие данные удалять нельзя.

Неуспешные сводки сохранены, но не считаются завершённым сценарием: `staged-fixture-1d9e30cf68d74795a215aa44e08597bf.json`, `staged-fixture-0ba9b50846fa4df5bd9a8ca797c2e7a9.json`, `staged-fixture-0ee6c6680fa44644b0ec90ec7310b283.json`. Во всех cleanup_ok=true. Диагностический бакет также удалён.

## Офлайн-проверки сохранённых данных

Без AWS/S3-переменных прочитаны пять сводок отдельных режимов через scan-report. У unsigned_readonly — код 0, у signed-проверок — ожидаемый 3 из-за недостатка baseline/частичных источников; у unsigned-мутаций — 3 из-за неопределённой полной уборки.

Экспорт: `.state/data/staged-export-3bb6578dcff547638c766005ec9c8725.md`, права 0600. Сводка сохраняет все три бакета, рекомендации и доказательства.

Внутренние отчёты сопоставляются прежним compare. Проверенная пара `45217dc2c341459f80b211410e2382a9` → `61edf61d07824c6abd9e4259475e6eeb` дала код 3/unverified из-за изменившегося охвата объектов. Это корректно: новые probe-ключи/остатки могут менять выборку. Нельзя выдавать такое сравнение за доказательство устранения всех рисков. Отдельные отрицательные запросы стадии closed_after и итоговая уборка при этом сохранены как реальные факты.

## Границы

- All — только бакеты, видимые данным ключам; без ключей нужны известные имена.
- Максимум 500 бакетов и 20 выбранных объектов на бакет; limited не означает полного охвата.
- Положительный Get/Write/Delete относится к точной цели. Delete подтверждает отсутствие текущего объекта, не уничтожение всех версий.
- Без signed-перечисления версий успешный DELETE не гарантирует полной уборки; нужен явный allow_residue.
- У сценария нет очереди/фоновой обработки/промежуточного checkpoint общего ScanRun при аварии процесса. Обычные внутренние отчёты сохраняются по мере обработки.
- Полный IAM, Condition/Not*, все версии/объекты, реальные права внешних субъектов и глобальная минимальность прав остаются ограничениями.
