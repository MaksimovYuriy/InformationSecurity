# Документация основной части

Документы описывают фактическое локальное приложение после рефакторинга. Основной технический контекст перед изменением кода — [PROJECT_SPECIFICATION.md](PROJECT_SPECIFICATION.md).

| Что нужно понять | Документ |
|---|---|
| Что реализовано, какие контракты приняты, что осталось | [Спецификация](PROJECT_SPECIFICATION.md) |
| Зачем нужны каталоги, кто кого вызывает, как расширять | [Архитектура](ARCHITECTURE.md) |
| Каждый модуль, класс, функция/метод, поле и константа | [Справочник исходного кода](CODE_REFERENCE.md) |
| Значение полей, версия схем, настройки и SQLite | [Модели и хранение](DATA_CONTRACTS.md) |
| Как выбрать несколько бакетов и пройти внешнюю/внутреннюю проверку | [Ступенчатый scan](STAGED_SCAN.md) |
| Как выполняется сканирование и работают все восемь правил | [Алгоритмы сканирования](SCANNING.md) |
| Почему выбраны эти правила и где границы проверки | [Каталог правил](rules/RULE_CATALOG.md) и связанные карточки |
| Как установить, настроить, запустить и показать исправление | [Руководство пользователя](USER_GUIDE.md) |
| Что проверяют все тестовые файлы и как запускать проверки | [Тестирование](TESTING.md) |
| Как требования задания связаны с проверенными результатами | [Матрица приёмки](ACCEPTANCE_MATRIX.md) |
| Что изменено в рефакторинге и чем это подтверждено | [Протокол итерации 10](ITERATION_10.md) |

Справочник кода строится скриптом `scripts/build_code_reference.py` из AST и docstring, включая закрытые методы и именованные локальные функции. Проверка `--check` обнаруживает рассинхронизацию. Архитектура, смысл данных, алгоритмы и ограничения описаны отдельно: перечень сигнатур их не заменяет. В исходниках есть docstring для каждого явно объявленного класса/функции/метода.

Документация тестов включает полный перечень сценариев; общие искусственные данные находятся в `tests/audit_fixtures.py`. Тесты названы по проверяемому поведению, без номера этапа.
