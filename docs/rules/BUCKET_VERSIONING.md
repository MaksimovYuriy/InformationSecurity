# Правило bucket-versioning-enabled, версия 1

## Угроза и границы

Без создания новых версий перезапись или удаление может привести к потере текущих данных. Правило включено как проверка возможности восстановления после ошибок пользователей и приложений. Оно не обнаруживает публичный доступ и не доказывает факт потери данных.

Версионирование не заменяет резервное копирование и защиту от удаления конкретных версий. Проверка не оценивает наличие пригодной истории версий, lifecycle, фактические права удаления, независимые резервные копии и успешность восстановления.

## Вход и алгоритм

Вход: наблюдение `versioning` из снимка бакета, метод `get_bucket_versioning`, поле `data.status`. Допустимые значения: Enabled, Disabled, Suspended. Охват — `bucket_configuration_only`.

- Enabled → `passed`: нарушение этого правила не обнаружено.
- Disabled/Suspended при включённом требовании `versioning` → `confirmed_violation`: подтверждено несоответствие настроенной базовой политике, а не ущерб.
- Disabled/Suspended при `required_controls: []` → `potential_risk`: рекомендованная мера не включена, обязательность не задана.
- Отсутствующее/недоступное/неподдерживаемое/повреждённое значение → `insufficient_data`; оценка риска неизвестна.
- Другой охват → `not_applicable`.

По умолчанию versioning — обязательная мера учебной базовой политики. Это выбор проекта, а не утверждение об обязательном требовании провайдера или законодательства.

Доказательство: поле, исходный метод, статус наблюдения и распознанное значение. MFA Delete для этого правила не используется; отсутствие поля не интерпретируется как выключенная защита.

## Опасность и исключения

Применяется модель риска v1 из протокола итерации 5. Возможные операции ущерба — overwrite/delete; их фактическая разрешённость и внешняя доступность здесь не анализируются. При неизвестной чувствительности: условная вероятность 2 × последствия 2 = 4, medium. При высокой чувствительности — 2 × 3 = 6, high. Это экспертная приоритизация, а не измеренная вероятность инцидента.

Для расходных учебных данных можно задать исключение с точным именем бакета, ID правила, причиной и необязательным сроком действия с часовым поясом. Исключение сохраняет исходный статус, риск и доказательство; причина находится в `exception_reason`. Недостаток данных не подавляется исключением. Активное исключение не является исправлением конфигурации.

## Рекомендация и подтверждение

При необходимости сохранения истории включить версионирование в настройках учебного бакета VK Cloud. До изменения учитывать увеличение занятого места и правила хранения версий. После включения переход обратно в исходное состояние без версионирования не предусмотрен, доступна приостановка.

Собрать новый снимок, подтвердить Status=Enabled и повторить правило. Восстановление проверить отдельным сценарием с искусственными объектами. Приложение настройки автоматически не меняет. Уже утраченные версии включение механизма не возвращает.

## Проверки

Enabled/Disabled/Suspended, неподдерживаемый API, отказ доступа, отсутствующие и повреждённые данные, исключение/его истечение/другой бакет, высокая чувствительность, необязательная мера. На реальном учебном бакете получен Enabled → passed. Небезопасные состояния проверены локальными данными, настройки облака для испытания не изменялись.
