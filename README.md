# Cloud Storage Audit

Служба проверки безопасности облачного хранилища. Реализованы окружение, демонстрационный сценарий, подключение к VK Cloud, список бакетов и сбор их конфигурации. Реализован движок с восемью правилами: версионирование, четыре анонимные операции и три проверки управления доступом; демонстрационный аудит отдельно помечается `simulated`. Анализ политик ограничен поддерживаемой частью модели, охват объектов задаётся явно.

## Локальный запуск

Требуется Python 3.12 или новее. Для профиля VK Cloud требуется boto3. Установите проверенный набор зависимостей:

```bash
.venv/bin/python -m pip install -r requirements.txt
```

Команда выполняется после создания виртуального окружения.

```bash
python3 -m venv .venv
cp .env.example .env
chmod 600 .env
set -a
. ./.env
set +a
PYTHONPATH=src .venv/bin/python -m cloud_audit check
PYTHONPATH=src .venv/bin/python -m cloud_audit --version
```

Пример `.env` содержит только безопасные настройки. Приложение читает переменные окружения; автоматическая загрузка `.env` не выполняется. Загружайте через shell только доверенный файл: shell исполняет его содержимое.

Команда `check` выводит JSON с версией, статусом, окружением и уровнем журналирования. Создаёт закрытые каталоги состояния, данных и журналов, проверяет возможность записи. Для `CLOUD_AUDIT_STATE_DIR` указывайте выделенный каталог приложения: его права и права подкаталогов `data`, `logs` устанавливаются в `0700`.

Коды завершения: `0` — успех, `1` — ошибка файлового доступа, `2` — неверные параметры, конфигурация или ошибка запроса, `3` — частичный снимок конфигурации. Для локального `check` настройки облака не требуются.

## Структура

- `src/cloud_audit/domain` — внутренние модели.
- `src/cloud_audit/application` — прикладные сервисы и интерфейсы внешних зависимостей.
- `src/cloud_audit/infrastructure` — конфигурация окружения и локальное хранение.
- `src/cloud_audit/cli.py` — консольная точка входа и сборка зависимостей.
- `tests` — тесты поведения и консольного запуска.

Используются SQLite и SDK S3; прежние JSON-отчёты доступны для чтения и явного импорта. Целевой запуск — локальный CLI; отдельный сервер и HTTP API не требуются. Итоговые испытания итерации 9 выполнены; далее — полный прогон тестов, документация и демонстрация основного сервиса (10), ИИ-помощник и дополнение документации (11). `pyproject.toml` описывает пакет и будущую установку; проверенный запуск из исходников выше требует runtime-зависимостей из requirements.txt, но не требует загрузки build-зависимостей.

## Консольный сценарий — итерация 2

Все команды ниже работают только с фиксированными демонстрационными данными. Профиль `demo` используется по умолчанию. Обращений к облаку и реального анализа безопасности нет; результаты имеют статус `simulated`.

```bash
PYTHONPATH=src .venv/bin/python -m cloud_audit connection --profile demo
PYTHONPATH=src .venv/bin/python -m cloud_audit resources --format text
PYTHONPATH=src .venv/bin/python -m cloud_audit audit --resource demo-public --rules demo-public-read
# Подставить id из результата audit:
PYTHONPATH=src .venv/bin/python -m cloud_audit report REPORT_ID --format text
```

Доступны ресурсы `demo-public` и `demo-private`. Если `--rules` не указан, выбирается единственный демонстрационный сценарий `demo-public-read`. Несколько правил передаются через пробел; неизвестные правила отклоняются.

С итерации 8 новые отчёты сохраняются между запусками в `CLOUD_AUDIT_STATE_DIR/data/audit.sqlite3` с правами `0600`; прежние JSON читаются совместимо и могут быть импортированы в историю. Для команд доступен `--help`; вывод по умолчанию — JSON, `--format text` добавляет заметную маркировку DEMO и форматирует данные для чтения.

Код `0` означает успешное выполнение команды, а не безопасность ресурса. Код `2` также используется для неизвестного ресурса, правила, профиля или отчёта; код `1` — для ошибок доступа к локальному хранилищу.

## VK Cloud — итерация 3

В существующий локальный `.env` перенесите названия полей из `.env.example`, заполните ключи и установите права `chmod 600 .env`. Не перезаписывайте существующий файл командой `cp`, если в нём уже есть ключи. Endpoint и ключи общие для всех доступных бакетов.

После загрузки доверенного `.env` в окружение (см. выше):

```bash
PYTHONPATH=src .venv/bin/python -m cloud_audit connection --profile vk
PYTHONPATH=src .venv/bin/python -m cloud_audit resources --profile vk --format text
```

`connection` проверяет авторизованное перечисление бакетов; успешный результат не подтверждает безопасность хранилища или минимальность прав. Ошибки облачного доступа возвращают код 2 без исходных сообщений SDK. `audit --profile vk` выполняет выбранные правила над свежим или сохранённым снимком (см. итерацию 5 ниже). Автоматической загрузки `.env` нет. Полный протокол, подготовка и удаление стенда: [итерация 3](docs/ITERATION_03.md).

## Снимок конфигурации — итерация 4

После загрузки окружения выберите бакет из `resources` и выполните:

```bash
PYTHONPATH=src .venv/bin/python -m cloud_audit collect --resource BUCKET_NAME --profile vk
# Подставить id снимка из ответа collect:
PYTHONPATH=src .venv/bin/python -m cloud_audit snapshot SNAPSHOT_ID --format text
```

Сбор включает ACL, политику, Block Public Access, Ownership Controls, версионирование, журналирование, шифрование по умолчанию и Object Lock на уровне бакета. Чтение сохранённого снимка работает без облачных ключей. Без дополнительных флагов объекты и их содержимое не перечисляются и не читаются; начиная с итерации 6 можно явно выбрать ACL объектов и включить ограниченные анонимные пробы (см. ниже).

Статусы каждой настройки: `available`, `absent`, `access_denied`, `unsupported`, `error`. Частичный снимок сохраняется, получает `collection_status: partial` и код завершения **3**, а не сообщение об успешной полной проверке. На учебном endpoint VK Cloud три метода вернули `unsupported`; это не доказывает отсутствие соответствующей защиты у провайдера. Снимок — входные данные аудита, а не заключение о безопасности.

Хранение: `STATE_DIR/data/snapshots`, каталог 0700, JSON 0600, версия схемы 1, лимит 2 МиБ. Срок — 7 суток: просроченные снимки недоступны для чтения и удаляются при следующем сохранении; фонового удаления нет. В снимках могут быть политики и идентификаторы доступа, поэтому не публикуйте их. Полный протокол и ограничения: [итерация 4](docs/ITERATION_04.md).

## Движок правил — итерация 5

Первое реальное правило — `bucket-versioning-enabled`; с итерации 6 в реестре также четыре правила анонимных операций. По умолчанию базовая политика требует включённого версионирования. Настройку политики можно задать через JSON по образцу `audit-policy.example.json`; в нём нет облачных ключей.

```bash
# Собрать свежие данные и выполнить правило:
PYTHONPATH=src .venv/bin/python -m cloud_audit audit --profile vk --resource BUCKET_NAME --rules bucket-versioning-enabled
# Повторить проверку сохранённого снимка без сети и ключей:
PYTHONPATH=src .venv/bin/python -m cloud_audit audit --profile vk --snapshot SNAPSHOT_ID --policy audit-policy.example.json
# Прочитать отчёт:
PYTHONPATH=src .venv/bin/python -m cloud_audit report REPORT_ID --format text
```

Для audit выбирается ровно один из --resource/--snapshot. Возможные результаты: `confirmed_violation`, `potential_risk`, `passed`, `insufficient_data`, `not_applicable`. Исключение сохраняет статус и оценку риска с объяснением в `exception_reason`. Отказ доступа не становится успешной проверкой.

Отчёт включает доказательства, риск, рекомендации, контекст политики и идентификатор снимка. Код 0 означает выполнение выбранных правил, включая возможные нарушения; код 3 — недостаток данных для хотя бы одного правила. Частичность общего снимка указана отдельно и не мешает оценке правила, если нужные ему данные получены. Правило версионирования не оценивает публичный доступ и не гарантирует восстановимость всех объектов.

Подробности: [итерация 5](docs/ITERATION_05.md), [карточка первого правила](docs/rules/BUCKET_VERSIONING.md).

## Анонимный доступ — итерация 6

В итерации 6 были зарегистрированы первые пять правил: версионирование и `anonymous-read`, `anonymous-list`, `anonymous-write`, `anonymous-delete`. Для конфигурационного анализа объектных операций выберите до 20 искусственных файлов через --objects; без выбора объектные результаты могут быть insufficient_data.

```bash
PYTHONPATH=src .venv/bin/python -m cloud_audit audit --profile vk --resource BUCKET_NAME --objects test.txt --probe-anonymous --rules anonymous-read anonymous-list
```

--probe-anonymous включает отдельный unsigned-клиент: список с MaxKeys=1 и чтение выбранных объектов с Range bytes=0-0, без сохранения их содержимого. Известное публичное разрешение без подтверждения — potential_risk, успешный unsigned-запрос — confirmed_violation. Condition и Not* пока не вычисляются и дают явное ограничение, а не уверенный вывод о закрытости.

Запись и удаление по умолчанию не выполняются. Дополнительный --allow-write-probes вместе с --probe-anonymous включает проверки только на генерируемых временных объектах `_cloud-audit-probe/<uuid>/`; нужны права подготовки и уборки, отсутствие Object Lock. Версии и маркеры очищаются. Ошибка уборки явно отражается в данных и коде 3; такие артефакты требуют внимания владельца стенда. Выбранные пользовательские файлы эти пробы не меняют.

Снимки используют schema_version=2; с итерации 8 новые отчёты используют v3 с версией правил и namespace ресурса. Старые v1/v2 читаются. Офлайн-аудит --snapshot не повторяет сохранённые пробы. Для самостоятельного изолированного испытания с новым временным бакетом:

```bash
PYTHONPATH=src .venv/bin/python scripts/verify_public_access.py --run-training-fixture
```

Сценарий ненадолго публикует один искусственный файл и список нового бакета, затем закрывает и удаляет стенд. Публичную запись не включает. [Протокол](docs/ITERATION_06.md), [проверка корректности](docs/CORRECTNESS_REVIEW_06.md), [правила](docs/rules/ANONYMOUS_ACCESS.md).

## Восемь правил — итерация 7

Окончательный набор описан в [каталоге](docs/rules/RULE_CATALOG.md). Дополнительно доступны `unapproved-external-access`, `excess-explicit-permissions`, `bucket-acl-disabled`.

Настройте контекст в своём JSON-файле по `audit-policy.example.json`:

- `trusted_project_ids`: собственные/доверенные проекты VK Cloud, не идентификаторы ключей;
- `allowed_external_accounts`: разрешённые внешние проекты либо точные субъекты;
- `required_permissions`: по одной записи subject/operations на субъект. Допустимы read/list/write/delete/read_acl/write_acl/read_policy. Пустой operations означает «никаких прав не требуется»; пустой required_permissions — отсутствие модели.

```bash
PYTHONPATH=src .venv/bin/python -m cloud_audit audit --profile vk --resource BUCKET_NAME --objects test.txt --policy audit-policy.example.json --rules unapproved-external-access excess-explicit-permissions bucket-acl-disabled
```

Пример с пустыми списками не заменяет фактическую baseline: без неё проверка избыточности возвращает insufficient_data. Анализируются только явные гранты в выбранном охвате, не полный IAM проекта. При рекомендуемом отключении ACL сначала проверьте совместимость загрузчиков; BucketOwnerEnforced не блокирует публичную политику сам по себе. Требование acl_disabled можно добавить в required_controls, если оно принято для проекта.

[Карточки новых правил](docs/rules/GOVERNANCE_ACCESS.md), [протокол итерации 7](docs/ITERATION_07.md). По согласованному режиму проверок в этой итерации запускались только новые тесты и затронутые прежние сценарии.

## История и сравнение — итерация 8

```bash
PYTHONPATH=src .venv/bin/python -m cloud_audit import-reports
PYTHONPATH=src .venv/bin/python -m cloud_audit history --resource BUCKET_NAME --severity high
PYTHONPATH=src .venv/bin/python -m cloud_audit report REPORT_ID --format markdown --output report.md
PYTHONPATH=src .venv/bin/python -m cloud_audit compare BEFORE_ID AFTER_ID --format markdown --output comparison.md
```

Эти команды работают без облачных ключей. История по умолчанию показывает vk; `--profile all` включает demo. Доступны фильтры правила, опасности и статуса, пагинация. Импорт сохраняет исходные JSON, экспорт создаёт новый файл 0600 без перезаписи. Фильтр отчёта явно помечает частичное представление и сохраняет общий статус.

Сравнение различает новые, сохраняющиеся, устранённые и неподтверждённые изменения. Для устранения нужны новое наблюдение и сопоставимый контекст; ранее подтверждённый анонимный доступ требует новых отрицательных unsigned-проб на тех же целях. Ошибка доступа, пропущенное правило или изменившийся охват не считаются исправлением. Несопоставимое сравнение возвращает код 3, failed-run без отчёта — 2. Подробности и реальные проверки: [протокол итерации 8](docs/ITERATION_08.md).
