# План разработки по итерациям

План разработки. Выбраны Python и VK Cloud Object Storage (S3); окончательный набор из восьми правил зафиксирован в docs/rules/RULE_CATALOG.md. Основной результат — локальное CLI-приложение, работающее с настоящим облачным хранилищем. По исходному заданию отдельный сервер, HTTP API и веб-интерфейс не обязательны и исключены из текущего объёма. ИИ-агент — дополнительная часть исходного задания, включённая в согласованный план после проверки основного сервиса; после него выполняется итоговое оформление.

Каждая итерация должна завершаться работающим результатом, который можно запустить и продемонстрировать. Организационные вопросы и распределение задач в этот документ не входят.

## Целевая последовательность

Локальное окружение → консольный запуск → подключение к облаку → модель конфигурации → движок правил → обнаружение публичного доступа → полный набор проверок → отчёты и повторный аудит → сквозные испытания локального сервиса → документация и демонстрация основного сервиса → ИИ-агент и дополнение документации.

## Итерация 1. Подготовка локального окружения

**Цель:** получить воспроизводимую среду запуска приложения.

Задачи:

- Выбрать базовый стек; предварительный вариант — Python, официальный SDK облака и SQLite. FastAPI не требуется для согласованного локального варианта.
- Подготовить локальное виртуальное окружение Python с воспроизводимым способом запуска.
- Создать структуру проекта, зафиксировать зависимости и пример конфигурации без секретов.
- Настроить безопасную конфигурацию и закрытые каталоги данных и журналов.
- Добавить минимальную команду проверки окружения и инструкцию запуска.

**Результат:** приложение запускается локально и выводит версию и состояние конфигурации.

**Критерий готовности:** по инструкции можно воспроизвести установку и запуск; секреты отсутствуют в репозитории и выводе команды.

**Статус:** завершена; результаты проверки — в [отчёте первой итерации](docs/ITERATION_01.md). Отдельный сервер не требуется в актуальном плане.

## Итерация 2. Консольный каркас

**Цель:** определить пользовательский сценарий до подключения реального облака.

Задачи:

- Реализовать команды проверки подключения, просмотра ресурсов, запуска аудита и получения отчёта. Названия команд уточнить при реализации.
- Определить параметры: профиль облака, целевой ресурс, набор правил и формат вывода.
- Реализовать загрузку конфигурации, понятные ошибки и коды завершения.
- Отделить консольный интерфейс от прикладной логики, для независимого тестирования и возможности добавлять другие интерфейсы.
- Проверить полный сценарий на явно обозначенных тестовых данных.

**Результат:** консольная версия выполняет демонстрационный аудит без реального облака.

**Критерий готовности:** успешный запуск и ошибки конфигурации различимы; демонстрационный режим явно указан в выводе.

**Статус:** завершена; результаты проверки — в [отчёте второй итерации](docs/ITERATION_02.md).

## Итерация 3. Подключение к облаку и учебный стенд

**Цель:** получать реальные сведения о хранилище.

Задачи:

- Выбрать провайдера и тип хранилища; далее предполагается объектное хранилище с бакетами.
- Создать отдельный учебный проект и закрытый бакет с искусственными файлами.
- Определить минимальные права аудитора и способ передачи учётных данных.
- Реализовать адаптер официального SDK: проверку подключения и получение списка ресурсов.
- Добавить обработку отказа в доступе, отсутствующего ресурса, сетевых ошибок и ограничений API.
- Подготовить инструкции создания и удаления стенда; учётные данные для изменения стенда отделить от прав аудитора.

**Результат:** консольная версия подключается к облаку и показывает реальные ресурсы.

**Критерий готовности:** список ресурсов соответствует стенду; недостаточные права выдаются как ошибка, а не как отсутствие нарушений.

**Статус:** завершена по решению пользователя от 22.11.2026. Адаптер и реальное подключение проверены; минимальность прав и отдельное сопоставление списка с кабинетом остаются неподтверждёнными и приняты как ограничения, не блокирующие переход к итерации 4. Подробности — в [протоколе](docs/ITERATION_03.md).

## Итерация 4. Сбор и нормализация конфигурации

**Цель:** сформировать достоверные входные данные для проверок.

Задачи:

- Получать доступные политики, ACL, ограничения публичного доступа и другие настройки, необходимые выбранным правилам.
- Определить охват объектов: настройки бакета, отдельные объекты или перечисление объектов с явно указанными ограничениями.
- Создать внутреннюю модель ресурса и конфигурации, независимую от консольного вывода.
- Отмечать отсутствующие, неприменимые и недоступные данные отдельно.
- Добавить безопасное сохранение снимка конфигурации для воспроизведения проверок; определить состав и срок хранения данных.

**Результат:** для учебного ресурса формируется структурированный снимок конфигурации.

**Критерий готовности:** данные сопоставлены с настройками облака; неполный охват не представляется как полная проверка.

**Статус:** завершена. Снимок учебного бакета получен и сохранён, ACL и версионирование сопоставлены с независимыми запросами к облаку. Неподдерживаемые API явно отражены в частичном снимке. Объекты не входят в охват; подробности — в [протоколе](docs/ITERATION_04.md).

## Итерация 5. Движок правил и модель риска

**Цель:** создать общий механизм выполнения проверок.

Задачи:

- Определить интерфейс правила: идентификатор, требуемые данные, применимость, логика, результат и рекомендация.
- Ввести статусы: подтверждённое нарушение, потенциальный риск, нарушение не обнаружено, недостаточно данных, неприменимо.
- Определить формат доказательств и уровни опасности.
- Подготовить методику оценки риска с учётом разрешённых операций и контекста данных.
- Добавить конфигурацию исключений, допустимых внешних аккаунтов и необходимых прав.
- Реализовать одно первое правило и проверить работу общего механизма.

**Результат:** аудит выполняется через единый движок, пригодный для добавления остальных правил.

**Критерий готовности:** правило возвращает воспроизводимый результат; исключение и нехватка данных обрабатываются явно.

**Статус:** завершена. Движок, пять статусов, модель риска, конфигурация контекста/исключений и правило версионирования реализованы. Реальный аудит VK Cloud и повторный офлайн-анализ проверены; протокол — [итерация 5](docs/ITERATION_05.md).

## Итерация 6. Обнаружение публичного доступа

**Цель:** реализовать центральное требование проекта.

Задачи:

- Реализовать проверки анонимного чтения, получения списка объектов, записи и удаления — в пределах модели доступа провайдера.
- Учитывать совместное действие политик, ACL, условий и явных запретов.
- Отделить вывод по конфигурации от фактического подтверждения анонимным запросом.
- Реализовать подтверждение чтения тестового объекта и получения списка без облачных учётных данных.
- Подтверждение записи и удаления выполнять только в явно включённом режиме на специально созданных объектах стенда.
- Для неподдерживаемых условий политик возвращать ограничение анализа, а не уверенный вывод о безопасности.

**Результат:** консольный аудит обнаруживает открытый доступ и объясняет источник разрешения.

**Критерий готовности:** открытая и закрытая конфигурации различаются; после закрытия доступа независимый анонимный запрос получает отказ.

**Статус:** завершена. Реализованы четыре анонимные операции, выбранные ACL объектов и unsigned-пробы. Реальный изолированный сценарий VK Cloud «закрыто → открыто → закрыто» прошёл, временный стенд удалён. Condition/Not* возвращают ограничения; положительные write/delete проверены локально в явно включаемом режиме. Протокол — [итерация 6](docs/ITERATION_06.md).

## Итерация 7. Полный набор правил и рекомендации

**Цель:** довести аудит до 6–10 обоснованных проверок.

Задачи:

- Выбрать дополнительные правила по возможностям API: внешний доступ, избыточные права, защита от случайной публикации, защищённый транспорт, журналирование, восстановление данных.
- Уточнить границы анализа избыточных прав: сравнивать с заданной моделью необходимых разрешений.
- Подготовить карточку каждого правила: угроза, входные данные, алгоритм, исключения, риск, исправление и способ подтверждения.
- Реализовать конкретные рекомендации для провайдера без использования ИИ.
- Проверить правила на безопасных, ошибочных и неполных конфигурациях.

**Результат:** полноценный консольный аудитор с окончательным набором правил.

**Критерий готовности:** реализовано 6–10 проверок; для каждой есть обоснование, проверяемое обнаружение и рекомендация.

**Статус:** завершена. Зарегистрированы восемь правил с карточками и рекомендациями; добавлены внешний доступ, избыточные явные права и отключение ACL. Пройдены 24 новых теста и 3 затронутые прежние проверки, выполнен реальный запуск VK Cloud без изменения доступа. Контекстно неполные результаты не выдаются за безопасность. [Протокол](docs/ITERATION_07.md), [каталог](docs/rules/RULE_CATALOG.md).

## Итерация 8. Отчёты, история и повторная проверка

**Цель:** сделать результаты пригодными для анализа и демонстрации исправлений.

Задачи:

- Сохранять запуски, параметры охвата и обнаружения в базе данных.
- Реализовать JSON и читаемый отчёт, например Markdown или HTML.
- Добавить фильтрацию по ресурсу, правилу и опасности.
- Сравнивать запуски по устойчивой идентичности ресурса и правила: новые, сохраняющиеся и устранённые нарушения.
- Не считать нарушение устранённым, если ресурс не проверен, изменился охват или возникла ошибка получения данных.
- Показывать время проверки, доказательства, ограничения и способ подтверждения исправления.

**Результат:** отчёты до и после исправления с объяснимым сравнением.

**Критерий готовности:** повторный аудит корректно показывает устранение проблемы; ошибка доступа не создаёт ложное сообщение об исправлении.

**Статус итерации 8:** завершена. SQLite, история, фильтры, JSON/Markdown, импорт и объяснимое сравнение реализованы. Пройдены 24 новых теста и 6 затронутых прежних проверок. Реальный VK Cloud подтвердил новые/устранённые read/list; ошибка запроса не выдана за исправление. [Протокол](docs/ITERATION_08.md).

## Итерация 9. Сквозные испытания локального сервиса

**Цель:** подтвердить соответствие локального приложения исходному основному заданию до подключения ИИ.

**Статус:** завершена. Восемь новых приёмочных методов (включая 24 сочетания матрицы), реальный VK Cloud «закрыто → открыто → закрыто», сравнение/экспорт и отказ аудита удалённого стенда проверены. Код ядра не менялся. По указанию пользователя запускались только новые тесты; полный регрессионный прогон — в итерации 10. [Протокол](docs/ITERATION_09.md), [матрица](docs/ACCEPTANCE_MATRIX.md).

Задачи:

- Подготовить матрицу «правило → конфигурация → ожидаемый результат».
- Выполнить основной сценарий: закрытое хранилище → публичный доступ → обнаружение → исправление → подтверждённый отказ в доступе → повторный аудит.
- Проверить исключения, нехватку прав, неполный охват и ошибки облачного API.
- Зафиксировать обнаружения, пропуски, ложные срабатывания и длительность аудита.
- Проверить установку и CLI-запуск по инструкции, сохранение истории между процессами и экспорт отчётов.
- Сопоставить каждое требование исходного задания с реализацией и доказательствами; отделить реальные облачные проверки от локальных тестовых данных.
- Сохранить протокол испытаний и инструкции воспроизведения.
- Проверить удаление тестовых объектов и возврат стенда в закрытое состояние.

**Результат:** проверенный основной сервис и доказательства выполнения обязательного задания.

**Критерий готовности:** все выбранные правила имеют результаты испытаний; основной сценарий воспроизводится без ИИ.

## Итерация 10. Документация основного сервиса и подготовка демонстрации

**Цель:** оформить проверенный проект для передачи и защиты.

**Статус:** завершена. Структура единого приложения перестроена по назначению, временный runner и устаревшие заглушки удалены, тесты переименованы по поведению. Полный набор: 134 метода, успешно в рабочем и чистом окружении; реальный цикл VK Cloud и сравнение после переноса проверены. Полная документация основной части — [карта](docs/README.md), изменения и проверки — [протокол](docs/ITERATION_10.md). Пояснительная записка по шаблону кафедры оформляется отдельно при предоставлении требований.

Задачи:

- Выполнить полный регрессионный прогон всех тестов по указанию пользователя и разобрать обнаруженные расхождения.
- Описать назначение, архитектуру, структуру модулей, зависимости, конфигурацию и локальный запуск.
- Свести обоснование восьми правил, методику оценки опасности, рекомендации и ограничения анализа.
- Подготовить руководство пользователя, протокол испытаний и сценарий демонстрации обнаружения и подтверждения исправления.
- После итерации 11 дополнить документацию описанием ИИ-помощника и результатами его оценки отдельно от основного аудита.
- При необходимости выполнить ограниченный рефакторинг структуры с сохранением поведения, совместимости данных и относящихся к изменениям проверок; обновить документацию после него.
- Если требуется пояснительная записка, оформить её по предоставленным требованиям кафедры.

**Результат:** документация соответствует фактическому коду, демонстрация воспроизводится локально.

**Критерий готовности:** все требования основного и выполненного дополнительного задания сопоставлены с проверенными результатами; известные ограничения явно обозначены, секретов в материалах нет.

## Итерация 11. Внедрение ИИ-агента

**Цель:** добавить помощника, который объясняет результаты и составляет план исправления конкретного хранилища.

**Статус:** не начата; дополнительная часть задания. Подключение через локальный интерфейс запуска, собственный HTTP API не требуется. Выбор локальной или внешней модели предстоит согласовать. Cloud.ru: простой агент с собственным MCP-сервером рассматривается как кандидат, а не принятое решение; Docker, размещение и стоимость уточняются только на этом этапе. VM заранее не арендуется.

Это последняя функциональная итерация. Основной аудит остаётся источником обнаружений и работает независимо от доступности модели.

Задачи:

- Выбрать модель, способ подключения и формат структурированного ответа.
- Предоставить агенту ограниченные инструменты чтения результатов, карточек правил и необходимой конфигурации ресурса.
- При необходимости добавить инструмент повторного аудита только для разрешённых ресурсов; права изменения облачных настроек не выдавать в базовом объёме.
- Подготовить проверенные сведения о способах исправления для выбранного провайдера.
- Формировать ответ: проблема, подтверждающие факты, последствия, последовательность исправления и проверка результата.
- Удалять секреты и лишние сведения из контекста модели; имена объектов и другие внешние данные обрабатывать как данные, а не инструкции.
- Проверять соответствие ответа фактам аудита; явно обозначать недостаток информации.
- Обрабатывать недоступность модели, тайм-ауты и некорректный ответ без потери основного отчёта.
- Оценить агента на заранее подготовленных нарушениях: правильность объяснения, применимость плана, отсутствие выдуманных настроек и опасного расширения доступа.
- Выполнить предложенные шаги на стенде и подтвердить результат обычным аудитом и независимым запросом.

**Результат:** агент объясняет реальные обнаружения и выдаёт проверенный на стенде план исправления.

**Критерий готовности:** агент использует результаты конкретного аудита, не выдаёт предположения за факты и не изменяет настройки самостоятельно; основной сервис продолжает работать при отказе ИИ.

## Технические решения для обсуждения перед детализацией

- Провайдер и тип сервиса хранения.
- Точный состав 6–10 правил и глубина анализа политик.
- Охват объектов и допустимые активные проверки.
- Детали воспроизводимой локальной установки и демонстрации; серверный интерфейс возможен только как отдельное будущее расширение.
- Форматы отчёта, хранение снимков и история.
- Модель ИИ, инструменты агента и источник сведений об исправлениях.

После обсуждения каждую итерацию можно разложить на задачи с зависимостями, входными данными и проверяемыми критериями готовности. Наличие ИИ-агента уже принято; обсуждению подлежит его техническая реализация.
