# Инструкции по разработке

Этот файл содержит согласованные правила разработки курсового проекта и применяется ко всему репозиторию.

## 1. Архитектура и масштабируемость

- Придерживаться Clean Architecture, принципов ООП и SOLID.
- Разделять сущности, прикладные сервисы и инфраструктурные реализации. Репозитории вводить там, где требуется доступ к хранимым данным.
- Направлять зависимости к внутренним слоям: сущности и прикладная логика не должны зависеть от CLI, веб-фреймворка, SDK облака или конкретной базы данных.
- Внешние интеграции подключать через интерфейсы и внедрение зависимостей.
- Обеспечивать возможность добавления правил, адаптеров провайдеров и интерфейсов запуска без переписывания основной логики.

## 2. Разработка через тестирование

- Работать по TDD: сначала написать тест на ожидаемое поведение и убедиться, что он падает по ожидаемой причине; затем реализовать код до прохождения теста.
- После прохождения тестов выполнять необходимый рефакторинг с сохранением их работоспособности.
- Изменения поведения и исправления ошибок также начинать с тестов.

## 3. Завершение итераций

- Не переходить к следующей итерации, пока текущая полностью не проверена на работоспособность.
- Проверять критерии готовности итерации, запускать относящиеся к ней тесты и проверять работоспособность ранее реализованного поведения.
- Подтверждать работу предусмотренным сценарием запуска; одних модульных тестов недостаточно для проверки интеграций.
- Если необходимая проверка недоступна или не пройдена, явно фиксировать это и не считать итерацию завершённой.

## 4. Секреты и конфигурация

- Не хранить секреты в публичном доступе и не добавлять их в Git.
- Для локальной разработки использовать переменные окружения или файл `.env`, исключённый из Git. При развёртывании допускается более подходящий механизм: менеджер секретов или штатная идентификация облачной среды.
- Хранить в репозитории только пример конфигурации, например `.env.example`, без реальных секретов.
- Не выводить секреты в журналы, отчёты и сообщения об ошибках и не передавать их ИИ-агенту.

## 5. Работа с репозиторием

- Не выполнять `git push` самостоятельно. Отправка изменений в удалённый репозиторий допускается только по явному указанию пользователя.

## 6. Описание проекта и спецификации

- Перед выполнением каждой задачи обязательно читать `docs/PROJECT_SPECIFICATION.md` и брать исходный технический контекст именно оттуда.
- При необходимости затем изучать относящиеся к задаче исходники, тесты и планы. Описание не заменяет проверку фактического кода.
- При изменении кода, контрактов, конфигурации или принятых технических решений актуализировать `docs/PROJECT_SPECIFICATION.md` в рамках той же задачи.
- Явно отделять реализованное и проверенное поведение от планов и ограничений. При обнаружении расхождений с кодом исправлять описание, не выдавая запланированное за готовое.
